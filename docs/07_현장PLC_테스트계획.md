# 07. 현장 PLC 사전 테스트 계획

- 배경: 실제 발주한 PLC로 정식 시운전을 해볼 여유가 없어서, 현장에 있는 **다른(목표 PLC가 아닌) PLC**에 지금 구현된 `server`/`hmi` 코드를 연결해 모터제어·센서신호 등이 정상 동작하는지 먼저 확인해본다. 정상 동작하면 프로그램(통신 계층·어댑터 로직)엔 문제없다고 판단하고, 실패하면 원인을 찾는다.
- 이 문서는 2026-09-02 대화에서 정리된 테스트 방침을 기록한 것이며, 실제 테스트 진행 상황은 이 문서를 갱신하며 추적한다.

## 전제 및 주의사항

1. **`registerMap.js`의 주소는 아직 미확정 "제안값"이다** (`docs/02_IO_태그맵.md` 참고). 테스트 대상 현장 PLC의 실제 주소와 다를 가능성이 크다. 그래서:
   - 테스트가 **실패**해도 프로그램 버그가 아니라 **주소 불일치** 때문일 수 있다 — 실패 원인을 바로 "프로그램 문제"로 단정하지 않는다.
   - 테스트가 **성공**해도, 이건 그 현장 PLC 기준 검증일 뿐 최종 발주 PLC와는 다를 수 있으므로 완전한 검증으로 보지 않는다.
2. 이 PLC에는 **실물 액추에이터(실린더·서보·펌프 등)가 물려있다.** 주소가 안 맞은 상태로 쓰기 명령을 보내면 의도와 다른 장치가 움직일 수 있다 — 쓰기 테스트 전에 항상 읽기부터 확인하고, 누군가 비상정지를 손에 두고 진행한다.

## 방법 — git 브랜치 분리

새 프로그램을 따로 만들지 않고, **git 브랜치**로 분리해서 지금 구현된 코드를 그대로 검증한다 (다른 코드를 테스트하면 검증 의미가 없어지므로).

- `server/src/io/motor|cylinder|sensor/*.js`, `wsServer.js`, `stateMachine.js` 등 모든 어댑터 코드는 `registerMap.js`를 **한글 키 이름**(`registerMap.coils.오토사이클_시작.addr` 등)으로만 접근하고 숫자 주소를 직접 쓰지 않는다 (2026-09-02 확인). 따라서:
  - 키 이름과 구조가 같고 **주소값만 다르면** → `registerMap.js` 파일 내용만 테스트 PLC 주소로 바꾸면 되고, 다른 코드는 수정할 필요 없음
  - 그 PLC의 신호 구성 자체가 달라서(신호 개수·종류가 다름) 키 이름/구조가 바뀌어야 하면 → 해당 신호를 참조하는 어댑터 코드도 함께 수정 필요

### 절차

1. 현장 PLC의 실제 I/O 주소 목록 확보 (사용자가 준비 중)
2. `git checkout -b test/현장plc` 로 테스트 브랜치 생성
3. 이 브랜치에서만 `registerMap.js`를 그 PLC의 실제 주소로 교체
4. **읽기부터 검증** — `readStatus` 계열 함수로 센서값이 그 PLC의 실제 상태와 일치하는지 확인 (쓰기 명령 이전)
5. 쓰기 테스트는 자동사이클이 아니라 **수동화면(manualScreen)에서 신호 하나씩** 확인
6. 테스트 중 실제 코드 버그(어댑터 로직, `client.js` 재접속 처리 등)를 발견하면 그 자리에서 고치고 커밋
7. 테스트 종료 후, **진짜 버그 수정 커밋만** `main`으로 cherry-pick/merge. `registerMap.js`를 테스트 PLC 주소로 바꾼 커밋은 `main`에 반영하지 않고 버린다 (실제 발주용 제안값은 `docs/02_IO_태그맵.md` 확정 전까지 그대로 유지)

## 완료 기준

- 모터제어(서보 X/Z, 파렛트 회전), 실린더 전후진, 센서 상태 읽기가 그 현장 PLC 기준으로 정상 동작 확인
- 위 항목은 통신 계층·어댑터 로직의 문제없음을 시사하는 참고 자료이며, **최종 발주 PLC와의 정식 통합테스트를 대체하지 않는다** (`PROJECT_PLAN.md` Phase 5/6 참고)
